# Evermore desktop build

Evermore uses Tauri 2. The Next.js UI is exported to static files, while
the existing Express/SQLite API runs as a bundled Node sidecar. Tauri uses the
system WebView2 runtime instead of shipping Chromium, so users do not need to
install Node.js or npm.

## Requirements

- Node.js 22 or newer (development/build only)
- Rust with the `x86_64-pc-windows-msvc` target
- WebView2 Runtime on Windows (Windows 10 and newer normally include it)

Install JavaScript dependencies, then start the desktop app in development:

```powershell
npm install
npm run desktop
```

The development launcher allows one session per project directory. Running the
command again brings the existing window to the front without restarting its
API or frontend. A new session cleans up processes left by an interrupted run;
if an open session has lost its development services, running the command again
restarts that session. Closing the desktop window also stops the launcher.

To check repeat launches, window restoration, service recovery, and interrupted
sessions on Windows, run `node --test scripts/test/desktop-startup.test.js`.
This check opens and closes the project's development window.

The Tauri build command creates an NSIS Windows installer in
`src-tauri/target/x86_64-pc-windows-msvc/release/bundle/nsis/`:

```powershell
npm run dist:win
```

`npm run build:desktop` only creates the static Next.js export. The Tauri build
hook stages that export, the API, its production dependencies, and the current
Node runtime under `src-tauri/resources/` before packaging them.

The local API stores `love-museum.sqlite`, `secret.key`, legacy `uploads/`, and
an automatically trimmed `media-cache/` in Tauri's per-user application data
directory. The media cache defaults to 500 MB, can be changed in Settings, and is safe to delete. Back up the whole directory,
including SQLite `-wal` and `-shm` files, while the app is closed. On Windows,
the app automatically keeps using `%APPDATA%\Love Museum` when it contains an
Electron database and the new Tauri data directory has no database yet. Data
from the old portable app's adjacent `LoveMuseumData/` directory must still be
copied manually after making a backup.

Evermore keeps the existing application identifier, database names, storage keys,
and sync object prefixes so data from Love Museum remains accessible.

The API test does not open a window and is useful for validating the local data
layer independently:

```powershell
npm run test:desktop-api
```

## Manual application updates

The Settings page only checks for updates when the user presses **检查更新**.
There is no startup check, timer, or background update request.

Generate the updater signing key once and keep the private key outside the repository:

```powershell
npx tauri signer generate --write-keys C:\secure\evermore-updater.key
```

For a signed release, set the object-storage latest.json URL, its public key,
and the private signing key, then build:

```powershell
$env:TAURI_UPDATER_ENDPOINT = 'https://updates.example.com/evermore/latest.json'
$env:TAURI_UPDATER_PUBLIC_KEY = '<public key generated by Tauri>'
$env:TAURI_SIGNING_PRIVATE_KEY = Get-Content 'C:\secure\evermore-updater.key' -Raw
$env:TAURI_SIGNING_PRIVATE_KEY_PASSWORD = '<key password>'
$env:TAURI_UPDATE_NOTES = '本次更新内容'
npm run dist:win
```

The build writes ready-to-upload files under release-updates/. Upload the
version directory first, then upload latest.json last. The endpoint and public
key are embedded into the release build; the private key is only used while
building and must never be uploaded. An unsigned development build keeps the
button disabled and does not contact an update server.

## S3-compatible sync

The desktop app can sync its SQLite database and uploaded media to a private
S3-compatible bucket. Open **对象存储同步** from the user menu, or use **从对象存储恢复数据**
on the login page when setting up an empty device. The connection requires an
Endpoint, Region, Bucket name, Access Key, and Secret Key.

Snapshots use the `love-museum/v1/` object prefix. The credentials need bucket
read/write access; deletion is not required. Credentials are encrypted in the
local application data directory and are not uploaded. Snapshot contents are
not additionally end-to-end encrypted, so keep the bucket private and enable
the storage provider's server-side encryption when available.

Sync is snapshot-based. When both the local and remote copies changed, the app
asks which copy to keep instead of merging silently. A cloud restore retains a
local recovery copy under `sync-recovery/` before replacing the database and
uploads directory.

New photo and video uploads are written directly under `love-museum/v1/media/`.
After a successful upload the local temporary file is removed. Media is downloaded
through the local API on demand and cached up to the user-selected limit; this cache is not included
in database snapshots. If object storage is not configured, uploads continue to use
the legacy local `uploads/` directory.
